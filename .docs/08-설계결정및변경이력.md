## OCR 실제 엔진 검토 — 2026-10-23

ADR-010: 실제 OCR은 PaddleOCR 한국어 모델을 우선 검증하고 EasyOCR·Tesseract를 비교 후보로 둔다. 공식 지원 자료에 근거한 잠정 결정이며 프로젝트 정확도·성능 실측 전이다. 현재 샘플 구현은 유지하며 실제 엔진 설치·연동은 아직 하지 않았다.

[OCR 엔진 선정 및 연동 계획](16-OCR엔진선정및연동계획.md)에 비교 기준, Java/Python 책임 경계, 현재 공급자 반환 계약의 확장 필요, 평가·장애 검증·완료 조건을 기록했다.

## 문서 OCR 엔진 명칭·범위 — 2026-10-23

ADR-011: 모듈명을 **문서 OCR 엔진**, 실제 연동 이후의 기술 범위를 **PaddleOCR 기반 문서 인식·검증 엔진**으로 정의한다. 인식 모델과 직접 개발할 처리·검증 코어를 구분한다. 기존 OCR 계획 문서를 0.2로 보강하고 현재 구현 범위와 OCR-AC 완료 기준을 추가했다. 실제 연동·평가 결과 보고서는 완료 후 별도로 작성한다. 이번 변경은 문서에만 적용한다.

## 가상 신청 문서와 정답 자료 — 2026-10-23

ADR-012: OCR 연동 전 내용이 일치하는 가상 신청서·증빙·견적서와 정답 JSON을 먼저 만든다. 숫자와 문구를 정확히 유지하기 위해 이미지 생성 모델 대신 코드 기반 PDF·PNG 생성을 사용한다. 정상 1건과 상호 불일치·견적 보완 변형을 제공하며 독립적인 정확도 평가 데이터셋으로 계산하지 않는다. 세부 내용은 [예시 신청서 및 검증 자료](17-예시신청서및검증자료.md)에 기록한다. 기존 자동 체험의 이미지 생성기는 이번에 교체하지 않았다.

ADR-012 보강: 외부·내부 현황을 설명하는 AI 생성 가상 사진을 추가했다. 기존 문서 4쪽은 보존하고 사진 포함 5쪽 버전을 별도 제공한다. 사진별 생성 표시와 위치·현황·개선 계획을 붙이고 원본·프롬프트를 보관한다. 사진에서 배선 상태를 단정하지 않는다.

ADR-012 서식 보강: 공공기관 제출 문서에 가까운 흑백 표 중심 5쪽 버전을 별도 제작했다. 제목 칸·접수 정보·본문 표·서명란과 사진대지의 테두리를 통일했다. 기존 PDF와 사진 원본은 보존한다. 공식 기관 로고·관인은 사용하지 않는다.

ADR-012 개정 2판: 참고 전북 PDF의 병합 셀·넓은 프레임과 수원 신청 서식의 확인표·상세 설명 구조를 참고해 7쪽 예시를 제작했다. 기존 금액을 유지하고 사업계획·일정·완료 확인 방법·견적 정보만 보충한다. 새 파일명과 v2 자료 폴더로 기존 산출물을 보존하며 실행 중 서비스는 변경하지 않는다.

## 문서 현황 동기화 — 2026-10-23

ADR-013: 일반적인 진입 파일명은 `README.md`를 사용하고 설명 본문은 한국어로 작성한다. 루트 `읽어주세요.md`와 산출물 안내 파일명을 변경했다.

ADR-014: 코드·원본 사진·정답은 Git에 관리하고 로컬 도구·생성 산출물·보관본·외부 참고 프로젝트·시크릿은 제외한다. 실제 기관 참고 서식과 이전 버전은 보관 폴더로 이동한다. ZIP은 삭제했으며 비교 이미지 재생성에서도 만들지 않는다.

초기 설계의 미구현 표기, DDL 상태, OCR·자료 제작 경계를 갱신했다. Java 테스트·HTTP·브라우저의 과거 검증 결과는 이번 문서 갱신에서 재실행한 결과로 바꾸지 않았다. 예시 자료 생성은 실제 OCR이나 앱 연결 완료를 뜻하지 않는다.

## 실제 OCR과 선택적 AI 보조 — 2026-10-23

ADR-014: PaddleOCR 3.3.3/PaddlePaddle 3.3.0 CPU API를 Java 작업 실행기에 연결한다. SAMPLE/LIVE/LIVE_AI를 별도 작업으로 보존한다. 외부 AI는 원문에 근거한 후보만 제안하며 자격·진위·선정 판단을 하지 않는다. NIM과 OpenRouter는 같은 요청 계약을 사용하되 자동 공급자 전환은 하지 않는다. AI는 전역·공간 일일 예약 한도와 1회 호출로 제한한다. 장애와 결과의 증거는 19번 보고서에서 관리한다.

## 신청·검토 업무를 기본 경로로 구성 — 2026-10-23

ADR-015: 일반 신청자는 계정으로 로그인해 빈 신청서를 만들고 직접 입력·업로드한다. 공고에 대상·지원 항목·제외·검토 기준·문의 정보를 보강하고 신청 정보에 사업장·업종·자부담을 추가한다. OCR 확인값은 사용자의 명시적 요청으로만 신청서에 반영한다. 담당자·관리자는 별도 업무 계정을 사용한다. 기존 격리 시나리오는 내부 회귀 검증용으로 보존하며 기본 메뉴에서 분리한다. V4 스키마와 최신 실행 증거는 20번 문서를 따른다.

## 콘텐츠와 시각 체계 개편 — 2026-10-25

ADR-016: `feat/content-design-refresh`에서 기존 미커밋 업무 구현을 보존하고 메인 정보 구조를 사업 탐색·서류 준비·신청 현황으로 구성한다. KRDS 원본은 수정하지 않고 서비스 CSS에서 청록·남색, 여백, 타이포그래피, 반응형 레이아웃을 적용한다. 직접 작성한 SVG 상점 그림을 사용하며 실제 기관 로고·지원 실적은 만들지 않는다. 공고 수·금액·기간·대상은 조회 결과를 출력하고 신청 안내·FAQ는 현재 구현 범위와 일치시킨다. 상세 접수 요약은 넓은 화면에서 고정하고 모바일에서는 본문 흐름으로 배치한다. 약관·개인정보 초안과 포트폴리오 안내는 유지한다. 참고: https://www.krds.go.kr/html/site/index.html (2026-10-25 확인). 커밋·원격 배포는 별도 검토 대기다.

## 실제 공공서비스 조사에 따른 디자인 기준 — 2026-10-25

ADR-017: 공식 eGovFrame 적용사례·적용점검 기록과 실제 사이트 10곳의 화면을 조사한 뒤 22번 디자인 규칙을 작성한다. 기존 임의 청록 테마와 장식 중심 SVG 히어로를 대체하고 공식 KRDS의 primary·gray 토큰을 참조하는 별도 서비스 테마를 적용한다. 메인 검색을 첫 화면의 실제 GET 폼으로 이동하고 업무 바로가기·공고·신청 안내·FAQ를 구성한다. 생성 일러스트는 보조 안내에만 사용하며 프롬프트·출처를 `.ref/service-visuals`에 기록하고 화면에 AI 제작을 표시한다. 공고 상세와 이용 안내에는 실제 본문 위치로 이동하는 목차를 추가한다. 업무 권한·상태·DB 규칙은 이번에 변경하지 않는다. ADR-016의 시안은 최종 디자인 근거로 사용하지 않으며 이번 기준으로 대체한다.

## 사업 정보 중심으로 메인 재구성 — 2026-10-25

ADR-018: 큰 검색 패널·반복 안내·메인 FAQ를 제거하고 조회된 공고의 본문·지원금·기간·서류와 신청 진입을 첫 영역에 구성한다. 대상·지원 항목·제외·검토 기준을 실제 공고 데이터로 보충하고 서류 준비와 처리 절차를 다른 시각 구조로 구분한다. 한글 서비스명과 공식 KRDS 아이콘을 사용하며 기존 생성 이미지는 보조 장식으로 축소한다. 신규 공고나 지원 실적은 만들지 않는다. 공통 헤더를 정리하고 푸터의 프레임워크 버전 문구는 사용자 업무에 필요한 안내로 대체한다. 첫 공고 선택은 기존 조회 순서를 그대로 따르며 추천·인기 순위 의미가 아니다. 22번 문서의 2차 기준을 따른다.

## 공고별 작성 완료 사례 — 2026-10-25

## 테스트 계정 입력과 공개 가입 분리 — 2026-10-25

ADR-036: 로그인 화면의 ‘테스트 계정 입력’ 버튼은 공개된 신청자 샘플 자격 증명만 채운다. 실제 로그인은 기존 인증 경로를 그대로 사용한다. 담당자·관리자 계정 자격 증명과 환경 변수의 별도 암호는 화면에 노출하지 않는다. 회원가입 화면은 브라우저 내 입력 형식 확인만 제공하며 폼 전송·브라우저 저장소 기록·계정 생성을 수행하지 않는다. RegistrationService는 내부 통합 검증용으로 유지하고 공개 HTTP에서 호출하지 않는다. 기존 계정·신청 데이터는 보존한다. 전체 HTTP 검증 스크립트도 테스트 계정 로그인과 공개 가입 차단을 검증하도록 변경한다. 커밋·푸시는 대기한다.

## 하단 스크롤의 고지 고정 보완 — 2026-10-25

## 문서 기반 신청과 검토 화면 — 2026-10-26

ADR-039: 신청은 직접 입력과 작성 문서 업로드를 함께 제공한다. 공고의 업로드 버튼은 선택 모달을 먼저 열고 실제 파일 제출 후 분석 작업을 생성한다. 통합 PDF와 개별 서류를 구분하며, 페이지 수와 문서 수를 분리해 연속된 다쪽 서류를 유지한다. 원본·실제 분할 PDF·추출 사진·필드 출처를 보존하고 검토 후 기존 ApplicationService로 반영한다. 제출본은 해당 분석 작업 식별자를 보존한다. 외부 AI 호출은 기본 경로에 필요하지 않다.

ADR-040: 검토 화면은 세로 나열 대신 원본과 검토 탭을 좌우 배치한다. 페이지 목록은 원본 왼쪽, 작은 화면에서는 원본 위쪽에 둔다. 신청 항목은 라벨·값·작은 원본 이동 버튼을 같은 행에 두고, 저장·취소와 이전 단계 이동을 명시한다. 반영 완료의 읽기 전용 상태를 편집 가능 상태와 구분하고 최종 제출 전 수정은 버전 검사를 거친다. 예시 업로드의 기본 파일은 기존 스캔 이미지 PDF이며 정답 JSON으로 인식값을 채우지 않는다.

## 문서 처리 중 로딩 표시 — 2026-10-26

ADR-041: 문서 처리 제목 옆에 작은 회전 서클을 표시한다. 서버의 QUEUED·PROCESSING 상태에서만 표시하고 READY·APPLIED·FAILED에서는 감춘다. 초기 화면과 상태 갱신 모두 같은 렌더링을 사용하고, 동작 줄이기 설정에서는 회전을 멈춘다. 실제 스캔 업로드의 PROCESSING에서 애니메이션 적용과 READY에서 숨김을 브라우저로 확인했다.

## 미사용 데모 화면 정리와 없는 주소 안내 — 2026-10-26

## 문서 선택·접수 분리와 중복 요청 복구 — 2026-10-26

ADR-043: 파일 선택은 브라우저 내 선택 상태만 바꾸며, ‘문서 접수·분석 시작’을 눌러야 파일을 전송한다. 접수 전 닫기·화면 이동은 분석을 만들지 않는다. 공고별 진행 중 접수 조회는 인증·소유권을 검사하고, 재진입 모달에 진행률과 ‘분석 이어보기’를 표시한다. 진행 중 다른 파일은 조용히 버리거나 새 작업으로 중복 생성하지 않는다.

접수 요청에는 파일 선택마다 UUID를 부여한다. V8의 신청별 고유 접수 키와 파일 내용 SHA-256을 이용해 같은 요청의 재시도는 기존 작업을 반환하고 같은 키로 바뀐 파일은 거부한다. 신청 행 잠금 안에서 조회·생성을 처리해 동시 요청을 직렬화한다. 뒤로가기 복원 시 버튼 비활성 상태를 풀고 서버 진행 상태를 다시 확인한다. 전송 응답이 늦으면 같은 접수 키로 재시도하며, 이미 진행 중이면 이어보기로 안내한다.

검증: Java 테스트 53개 통과. 실제 MariaDB에서 동일 키 재사용·내용 변경 거부·진행 중 중복 방지·완료 후 재시도 재사용을 검증했다. 로컬 HTTP 동시 요청 2건이 분석 12번 하나만 생성했고 완료 후 재요청도 12번으로 돌아갔다. 브라우저에서 선택·닫기·다른 화면·뒤로가기 동안 새 접수가 생기지 않았고, 명시적 접수 후 분석 13번으로 이동했다. 즉시 뒤로가기 후 재진입에서는 13번 진행률과 이어보기만 제공했다. 실제 네트워크 단절 자체를 재현한 검증과 요청 재전송 검증은 구분한다.

## 업로드 완료 화면에서 명시적으로 분석 시작 — 2026-10-26

ADR-044: 업로드와 분석을 서버 상태에서도 분리한다. 업로드 POST는 파일을 저장한 UPLOADED 상태로만 종료하며 다음 원본 확인 화면을 보여준다. GET·새로고침·뒤로가기·서버 재시작은 상태를 바꾸지 않는다. 확인 화면의 별도 POST /applications/{id}/intake/{intakeId}/start에서 소유권·DRAFT·분석 상태를 검사한 후에만 QUEUED로 변경한다. 스케줄러는 QUEUED만 가져간다. 중복 시작은 재실행하지 않고 원래 작업을 유지한다. ADR-043의 분석 시작 위치는 이 결정으로 대체한다.

업로드 모달은 기존 파일 탐색기의 폴더·파일 아이콘·선택 강조·우측 미리보기·하단 파일명과 업로드 버튼을 재사용한다. 원본 확인 PDF는 view=Fit로 한 페이지 전체를 표시한다. 원본 파일명은 권한 검사 후 UTF-8 Content-Disposition으로 제공해 f.txt 임시 이름을 방지한다. PDF 페이지 맞춤 동작은 Chromium의 open_pdf_params_parser.ts에서 확인했다: https://chromium.googlesource.com/chromium/src/+/HEAD/chrome/browser/resources/pdf/open_pdf_params_parser.ts

검증: Java 테스트 53개 통과. 실제 DB에서 업로드·반복 조회의 UPLOADED 0% 유지와 스케줄러 claim 거부, 명시적 시작 후 QUEUED 변경, 타인 시작 거부·중복 시작 재실행 방지를 확인했다. 실제 브라우저 업로드 15번은 원본 확인 페이지를 반복 조회하고 서버를 재시작해도 분석하지 않았으며, 분석 시작 버튼 클릭 시에만 실행 로그가 남았다. 동일 화면에서 전체 페이지 맞춤과 업로드 파일명 표시도 확인했다. 커밋·푸시는 대기한다.

2026-10-26. 공개 검토 데모 확인 중 만료 수거와 결과 저장의 기본키·상태 인덱스 잠금 순서 충돌을 발견했다. 만료 수거는 LIVE 작업과 만료 임대 구간만 전용 복합 인덱스로 검색한다. PREPARED 작업에 임대를 부여하거나 정상 결과를 실패로 덮지 않는다. V12와 기존 회귀 테스트를 보완했고 실제 MariaDB 동시 실행으로 데모·만료·유효 작업의 상태를 확인했다. 상세는 33번 문서를 따른다.

ADR-054 후속: V12와 수정 이미지를 운영에 반영했다. 공개 데모 READY 후, 이미지 생성 종료 상태에서 새 실제 검토도 READY·AI SUCCEEDED·원문 검증 20건·PNG 200으로 완료했다. DB 교착 실패와 부하 중 중단된 검증은 성공 결과에서 제외한다. 커밋·푸시는 보류했다.

## 외부 구성요소 고지와 정부 사이트 캡처 제거 — 2026-10-26

## ADR-055 MVC 계층별 패키지로 코드 배치 정리

기능별 폴더 안에 Controller·Service·Mapper가 혼재하던 구성을 `controller`, `service`, `mapper`, `dto`, `model` 중심으로 정리했다. 업무 규칙은 `service.policy`, 인증 주체·접근 검사는 `security`, 파일 처리는 `storage`, 공급자 호출은 `integration.ocr`, 실행기는 `scheduler`로 분리한다. Java 본체 82개와 테스트 17개의 참조를 갱신했다.

## ADR-056 관리자 계정의 직접 접수 검토

혼자 업무 흐름을 확인할 때 관리자와 담당자 로그인을 번갈아 하는 불편을 줄인다. 기존 검토 화면·Service를 재사용하고 `/staff/**`에 관리자 접근을 허용한다. `AccessScope.reviewer`는 관리자의 같은 공간 접근과 담당자의 배정 접근을 구분한다. 관리자는 담당자 배정 없이 시작·보완 요청·결과 확정이 가능하다. 신청자 접근 차단, 공간 격리, 상태·버전 검사, 이력·트랜잭션은 유지하며 DB 구조는 변경하지 않는다.

## ADR-057 역할별 안내와 공통 변경 확인 모달

사용자와 관리자 흐름을 금색·핑크색으로 구분하고, 로그인 선택 후에는 실제 역할과 화면의 업무 상태에 맞는 다음 조작 하나를 안내한다. 권한·진행 상태는 서버가 관리하며 안내가 자동으로 신청·검토 결과를 생성하지 않는다. 네이티브 confirm 세 곳은 공통 dialog로 교체해 선택 결과 확인, 취소/ESC, 포커스 복원과 원래 폼 검증을 일관되게 적용한다.

## ADR-058 확정 사유 입력 보조

계정별 업무 확인 중 반복 입력 부담을 줄이기 위해 선정·미선정별 고정 문구를 브라우저에서 제공한다. 외부 AI를 호출하거나 결과를 자동 판단하지 않는다. 마지막 자동 문구와 현재 입력값을 비교해 결과 변경 시 자동 문구만 갱신하며 직접 수정한 사유는 보존한다. 자동 입력은 제출을 유발하지 않고 기존 검토 확인·최종 모달·서버 검증을 유지한다.
