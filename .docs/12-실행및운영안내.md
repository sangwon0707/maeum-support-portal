# 실행 및 운영 안내

갱신일: 2026-10-26. 실행 명령과 현재 서비스 흐름을 기준으로 정리했다.

## 준비 사항

Java 21, Maven, Docker Compose가 필요하다. 공식 eGovFrame 5.0.2는 고정 태그·커밋으로 사용한다. 필요한 Maven 패키지가 없으면 `scripts/bootstrap-framework.sh`가 공식 소스를 내려받아 로컬에 설치한다. `.ref/`와 `.tools/`는 새 체크아웃에 포함되지 않으며 공개 출처는 [출처 기록](references/SOURCE_PROVENANCE.md)을 따른다. Java PDF 모듈은 Java 17 이상에서 실행되며 개발·앱 빌드는 Java 21을 사용한다.

## 로컬 앱 실행

```bash
./scripts/dev.sh
```

MariaDB를 준비하고 필요한 공식 의존성을 확인한 뒤 내장 Tomcat으로 실행한다. 기본 주소는 http://127.0.0.1:8087 이다. JDK가 `.tools/`에 없으면 `JAVA_HOME`으로 Java 21을 지정한다. 이 스크립트는 환경 파일을 자동으로 읽지 않으므로 실제 OCR·DB 설정을 사용할 때는 실행 셸에 먼저 내보낸다.

```bash
set -a
for config_file in .env.ocr .env.local .env.ai.local; do
  if [ -f "$config_file" ]; then
    source "$config_file"
  fi
done
set +a
./scripts/dev.sh
```

환경 파일은 실행 가능한 셸 설정이므로 직접 관리하는 파일만 읽는다. 키·비밀번호를 터미널 출력이나 소스에 복사하지 않는다. 종료는 실행 터미널에서 Ctrl+C이며 DB·파일 볼륨은 삭제하지 않는다.

## Tomcat 컨테이너 실행

```bash
./scripts/test.sh
docker compose -p egov-portfolio -f compose.yml -f compose.app.yml up -d --build app
```

`test.sh`는 별도 테스트 스키마를 사용하고 Maven verify로 WAR를 만든다. 앱 주소는 http://127.0.0.1:8088 이며 `target/support-portal.war`가 ROOT.war로 들어간다. DB·파일을 공유하는 앱을 두 방식으로 동시에 실행하지 않는다. 종료는 같은 Compose 구성의 `stop app`을 사용하며 볼륨을 삭제하는 명령과 구분한다.

## OCR·PDF·AI 실행

이미 준비한 로컬 OCR Python 환경은 다음 명령으로 시작한다.

```bash
./scripts/ocr-dev.sh
```

이 스크립트는 PDFBox 모듈을 빌드하고 `.env.ocr` → `.env.local` → `.env.ai.local` 순으로 설정을 읽은 뒤 루프백 8091에서 API를 실행한다. `.tools/ocr-venv` 설치가 선행되어야 한다. 실제 Linux OCR Docker 이미지는 linux/amd64에서 검증했다. 기반 휠과 하드웨어가 다른 환경의 설치 성공까지 보장하는 명령은 아니다.

Compose에서는 `compose.yml`, `compose.app.yml`, `compose.ocr.yml`을 함께 사용한다. `OCR_API_TOKEN`은 앱·OCR에 동일하게 설정한다. `OCR_LIVE_ENABLED`는 실제 문서 엔진, `OCR_AI_ENABLED`는 외부 AI 보조 사용 여부다. 공급자는 `AI_PROVIDER`, 키는 선택한 공급자의 서버 환경변수로 전달한다. 기본값은 외부 AI 비활성이며 Oracle 운영 환경에서는 OpenRouter Gemma 4를 명시적으로 활성화했다.

문서 검토 데모는 별도 OCR·LLM을 호출하지 않고 `src/main/resources/prepared-intakes/`의 결과를 사용한다. 실제 검토는 새 인식을 수행한다. 작업 시간이 길다고 고정 응답으로 전환하거나 공급자를 자동 재시도·전환하지 않는다.

## 현재 기본 업무 흐름

1. 로그인 화면의 왼쪽 사용자 테스트 계정 또는 오른쪽 관리자 테스트 계정 → 로그인 → 공개 계정·개인정보 금지 안내 확인 → 홈으로 이동한다. 공개 회원가입은 실제 계정을 생성하지 않는다.
2. 공고에서 직접 작성 또는 작성 문서 업로드를 선택한다.
3. 직접 작성은 신청 정보를 입력하고 증빙 이미지를 첨부한다. 작성 문서 업로드는 한 묶음 PDF를 모달에서 선택하거나 직접 올린다.
4. 업로드 후 원본 확인 화면에서 UPLOADED 상태를 유지한다. 사용자가 ‘문서 검토 요청’을 눌러야 시작한다.
5. 데모 또는 실제 검토를 선택한다. 실제 검토의 처리 시간·외부 AI 전송 안내를 확인한다.
6. 원본·추출 항목·분할 문서·사진을 대조하고 수정한 뒤 신청서에 반영한다. 검토 완료만으로 제출되지 않는다.
7. 최종 제출 후 관리자로 로그인해 `/admin`의 접수 검토하기를 누른다. 별도 배정 없이 검토 시작 → 보완 요청 또는 결과 확정 → 신청자 나의 신청 조회로 진행한다. 담당자에게 배정해 처리하는 기존 흐름도 사용할 수 있다.

`/demo` 시나리오 선택 화면은 삭제되어 404를 반환한다. 일반 신청자가 담당자로 역할을 바꾸는 기능을 공개 흐름으로 제공하지 않는다. 담당자·관리자 계정은 로컬 업무 검증과 서버 권한 통제를 구분한다.

## 공개 계정·저장 자료

`LOCAL_SEED=true`는 개발·포트폴리오 배포의 초기 계정·공고를 준비한다. 공개 테스트 비밀번호와 실제 DB·OCR 토큰을 혼동하지 않는다. 운영 시드의 공개 계정은 여러 방문자가 함께 사용하므로 실제 개인정보를 저장해서는 안 된다. 기존 계정 비밀번호는 시드 재실행으로 바뀌지 않는다.

공개 계정 신청 자료는 매일 한국시간 04:00 기준으로 정리하고 진행 중 작업은 보호한다. 저장 파일은 내용 주소로 공유하며 미참조 파일은 보호 기간 후 수거한다. 새 인식을 수행하는 실제 검토에서도 같은 파일 바이트를 중복 저장할 필요는 없다. 정책·제한·동시성 경계는 [30번 문서](30-자료초기화및저장공간관리.md)를 따른다.

## 검증과 포맷

```bash
./scripts/test.sh
./scripts/format.sh --check
python3 scripts/check-publication.py
```

통합 테스트 스키마는 `support_portal_test`, 파일 경로는 `.local/test-files`다. 전체 검증은 PDFBox·Java/MariaDB를 포함하며 OCR Python 환경이 있을 때 Python 테스트도 실행한다. Python 환경이 없으면 해당 테스트가 실행되지 않으므로 전체 숫자를 같은 것으로 표시하지 않는다. 현재 파일의 공개 검사와 과거 Git 이력 검사는 다른 절차다.

## 운영 배포와 백업

Oracle 무료 VM의 앱·DB·OCR Docker Compose와 호스트 Caddy·Cloudflare HTTPS를 사용한다. 실제 배포·Fail2ban·공개 검토 증거는 [31번 문서](31-오라클무료서버배포.md), PDFBox 회귀는 [33번 문서](33-PDFBox전환및회귀검증.md)에 있다. GitHub Actions는 비활성화했으며 Git 커밋·푸시·PR을 배포 명령으로 사용하지 않는다.

DB와 파일 볼륨을 함께 보존해야 제출본을 복원할 수 있다. 전체 백업 자동화와 별도 환경의 완전 복원은 검증 완료로 표시하지 않는다. Oracle Cloud 배포와 Oracle Database 호환성도 별개이며 후자는 미검증이다.

## 자료·고지 관리

가상 제공 PDF·사전 인식 산출물은 서비스에 필요한 파일로 관리한다. `output/`의 제작·검토용 임시 PNG와 로그는 새 체크아웃에 없을 수 있다. 재생성은 [17번 안내](17-예시신청서및검증자료.md), 라이선스는 [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md)를 따른다.

최근 정부 캡처·미사용 상징 제거와 고지 파일 정비를 소스에 적용하고 고지·CSS·미사용 상징 삭제는 서버 정적 파일에도 반영했다. 전체 앱 이미지 재배포·컨테이너 재시작·DB 변경은 하지 않았다. 정적 파일의 컨테이너 재생성 이후 유지 여부는 배포 이미지 갱신과 구분한다.

## 계층별 코드와 실행 진입점

Controller·Service·Mapper·DTO·Model은 각 역할별 패키지에 있다. 실행 진입점은 기존 `kr.co.maeum.support.config.LocalServer`와 Spring 설정을 유지하며 실행·테스트 명령은 동일하다. MapperConfigurer가 `kr.co.maeum.support.mapper`를 스캔하고 `classpath:mapper/*.xml`을 읽는다. 변경된 폴더를 수동 classpath에 추가할 필요는 없다.
