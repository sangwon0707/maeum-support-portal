# 문서 기반 신청 구현과 검토 계약

갱신일: 2026-10-26. 초기 PyMuPDF·개별 업로드·분석 시작 설계와 검증은 [이전 기록](archive/29-previous.md)에 보존한다. 현재 PDF 처리기는 Apache PDFBox 3.0.8이다.

## 입력 경로

직접 폼 입력과 작성 문서 업로드를 제공한다. 공개 문서 모달에서는 작성한 신청서·계획·증빙·사진이 들어 있는 PDF 한 묶음을 고른다. 개별 이미지 증빙 첨부는 직접 작성 흐름에서 지원한다. 내부 API의 SEPARATE 구성 지원이 공개 화면의 다중 파일 선택 제공을 의미하지 않는다.

업로드 API는 원본 저장만 수행한다. 모달 열기·취소·뒤로가기·새로고침이 인식 요청을 대신하지 않는다. 원본 화면에서 UPLOADED를 확인하고 ‘문서 검토 요청’을 눌러야 시작한다. 손상·암호·형식·크기·쪽수 검사는 처리 계약에 따라 수행하며, 실패를 숨기기 위해 사전 정답으로 전환하지 않는다.

## 처리와 화면

- PDFBox Java 모듈은 텍스트·좌표·렌더링·이미지 영역·실제 분할 PDF를 처리한다. 텍스트 없는 페이지는 실제 검토에서 PaddleOCR로 읽는다.
- LLM이 활성화된 실제 검토에서는 문서 전체 추출 문구를 선택한 공급자로 보내 종류·항목 후보를 받는다. 원문에 없는 값은 제외한다.
- 데모는 제공한 7종 스캔의 사전 결과를 불러오며 새 OCR·LLM을 호출하지 않는다. 실제 검토는 결과 캐시로 대체하지 않고 새로 처리한다.
- 결과 화면은 원본·페이지 목록과 신청 내용·분할 문서·사진/표를 함께 보여준다. 페이지 목록은 원본 옆 또는 위에 두고 본문 항목은 간결한 인라인 입력으로 편집한다.
- 사용자 확인 전 신청서 값을 자동 덮어쓰지 않는다. 종류·경계·항목·사진을 수정하고 신청서 반영을 명시적으로 선택한다.
- 분류·OCR·AI는 문서 진위·실제 사업자·지원 자격·선정을 보증하지 않는다. 견적 표는 원문 행을 제공하며 완전한 품목별 업무 데이터베이스로 확정하지 않는다.

## 상태·권한·파일

작업은 UPLOADED → QUEUED/PROCESSING → READY → APPLIED를 따르며 오류는 FAILED로 남긴다. PREPARED는 사용자 요청 후 PROCESSING으로 재생한다. 원본·파생 PDF·사진은 소유권 검사로 접근하고 신청서 반영은 소유자의 DRAFT에 제한한다. 제출 이후 해당 제출본을 임의 변경하지 않는다.

파일당 10MiB, 작업 최대 12쪽을 적용한다. 원본·파생 파일은 SHA-256 내용 주소로 공유하되 신청·제출 기록은 별도로 유지한다. LIVE 작업 만료 수거는 V12 전용 인덱스로 범위를 좁혀 데모 결과 저장과의 교착을 방지한다.

## 검증

로컬 실제 스캔 PDF·원문·분할·사진·수정·반영·제출·배정 전후 접근을 검증했다. 공개 사이트에서는 업로드 후 대기, 검토 데모 READY, 실제 텍스트 PDF의 READY·AI 성공·이미지 200을 확인했다. 자세한 테스트 수·처리 시간과 입력 차이는 [33번](33-PDFBox전환및회귀검증.md)을 따른다. 공개 사이트 전체 최종 제출·담당자 검토까지 이번에 모두 재실행했다고 표시하지 않는다.

## 현재 코드 탐색 경로

`controller/IntakeController` → `service/IntakeService` → `mapper/IntakeMapper`가 업로드·요청·조회·반영을 처리한다. 실행은 `scheduler/IntakeWorker`·`PreparedIntakeWorker`, 공급자 호출은 `integration/ocr/IntakeProvider`, 파일은 `storage/IntakeStorage`에서 담당한다. 모두 `src/main/java/kr/co/maeum/support/` 아래 경로다. SQL XML과 JSP 위치는 유지하며 클래스 배치 변경으로 요청·응답 계약을 바꾸지 않았다.
