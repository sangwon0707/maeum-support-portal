# 공개 계정 자료 초기화와 저장 공간 관리

작성일: 2026-10-26

## 처리 기준

공개 계정 `applicant`의 신청 자료는 한국시간 매일 04:00을 기준으로 초기화한다. 04:00 이후 생성한 신청은 다음 날 대상이다. `application.created_at`은 수정 시각과 분리하므로 내용을 수정해서 보관 기간이 계속 연장되지 않는다. 기존 자료는 기능 도입 시각으로 생성 시각을 부여해 도입 직후 소급 삭제하지 않는다.

스케줄러는 5분마다 기준 시각 이전 신청을 최대 100건씩 정리한다. 서버가 04:00에 꺼져 있었으면 재개 후 누락분을 처리한다. 요청 중인 업로드·반영은 같은 신청 행 잠금으로 직렬화하고, QUEUED·PROCESSING 문서 작업 또는 PENDING·RUNNING OCR이 있는 신청은 완료·실패 처리 후 다음 정리 주기에 처리한다. 사용자·권한·공고·배포용 샘플과 `.ref`·프로젝트 문서는 지우지 않는다. 로그인 이름과 소유 공간을 서버에서 재확인한다.

SQL은 MaintenanceMapper XML에 둔다. 신청별 트랜잭션에서 확인값·OCR 결과/작업·제출본 서류 연결·보완 응답/항목/요청·명령·제출본·첨부·원본 접수·검토·배정·상태 이력·감사 기록을 자식부터 삭제한 뒤 신청을 삭제한다. 중간 실패 시 해당 신청 전체를 롤백한다. 이미 삭제한 건은 재실행해도 영향을 주지 않는다. FK 검사를 끄거나 공용 테이블을 비우지 않는다.

## 동일 파일의 저장과 OCR 결과 재사용

- 원본, 이미지, 사진, 분할 PDF는 SHA-256 내용 주소로 저장한다. 같은 영역에서 내용이 같으면 파일을 다시 쓰지 않는다. 신청·첨부 버전 기록은 각각 유지하며 참조만 공유한다. 기존 UUID 키도 계속 읽을 수 있다.
- 파일 공유 때문에 document.storage_key의 단독 고유 제약만 일반 인덱스로 변경한다. 신청·문서 종류·버전 고유 제약은 유지한다. 파일 다운로드는 기존 신청·접수 소유권 검사를 거치므로 해시를 아는 것만으로 접근할 수 없다.
- 통합 문서의 실제 엔진 출력은 사용자 수정 전 원형으로 별도 캐시한다. 공간·소유자·업로드 내용과 종류/순서/구성 해시·처리 버전이 모두 같을 때만 재사용한다. 기존 사용자 확인값과 제출 내용을 재사용하지 않는다. 다른 소유자 캐시는 재사용하지 않는다.
- 재사용 시 새 원본의 ID·파일명으로 페이지·분류·항목 근거를 다시 연결한다. 참조 파일이 하나라도 사라졌으면 실제 인식을 다시 수행한다.
- 업로드만으로 캐시나 사전 결과를 반영하지 않는다. UPLOADED와 원본 확인 화면을 유지한다. 현재 OCR 실제 검토는 새 공급자 처리를 수행해 실제 결과 캐시 재사용을 건너뛴다. OCR 검토 데모는 사용자 요청 뒤 사전 결과를 재생하며 시간 기반 표시를 사용한다. 파일의 동일 바이트 저장 재사용과 인식 결과 재사용은 별개다.
- 모델·전처리·문서 분류/추출/분할 규칙을 바꾸면 DOCUMENT_PIPELINE_VERSION을 반드시 올린다. Python 분할 PDF는 매번 새 파일 ID를 만들지 않도록 no_new_id=True를 사용한다.

## 미참조 파일 수거와 용량 제한

DB 삭제와 파일 삭제는 하나의 원자적 트랜잭션이 될 수 없다. 따라서 DB 기록을 먼저 삭제하고, 참조가 사라진 파일을 별도 수거한다. DB 삭제 후 파일 수거 전에 서버가 종료되어도 다음 실행에서 이어서 수거한다.

수거 시 모든 첨부, 업로드 원본, 인식 결과 JSON, 유효한 실제 인식 캐시에서 현재 파일 참조를 모은다. 다른 신청·소유자가 사용 중인 파일은 남긴다. 생성 후 1시간이 지난 미참조 파일과 중단된 임시 업로드만 제거한다. 따라서 초기화 직후 곧바로 모든 바이트가 줄어드는 것은 아니며, 최근 파일은 보호 시간이 지난 후 정리한다. 공유 파일은 개별 업로드 롤백 때 즉시 삭제하지 않는다.

StorageGuard는 저장 트랜잭션 종료와 OCR 파일 생성·결과 저장까지 수거를 막는다. 파일 쓰기는 직렬화하여 동시 요청이 용량 검사를 함께 통과하지 못하게 한다. 내용 주소 저장은 원자적인 파일 이동으로 완료하여 부분 파일을 정상 파일로 사용하지 않는다.

| 환경변수 | 기본값 | 의미 |
| --- | --- | --- |
| PUBLIC_DEMO_LOGIN | applicant | 정기 초기화 대상 공개 계정 |
| FILE_MAX_BYTES | 536870912 | FILE_ROOT 안의 전체 파일 상한 512MiB |
| FILE_MIN_FREE_BYTES | 1073741824 | 저장 후에도 남겨 둘 디스크 여유 1GiB |
| DOCUMENT_PIPELINE_VERSION | pdfbox-3.0.8-paddle-v5-ko-layout-v2 | 실제 인식 캐시 처리 버전 |

새 파일이 한도를 넘으면 저장 전에 507 업무 오류로 거부한다. 이미 존재하는 동일 파일은 추가 용량이 필요하지 않아 한도 상태에서도 재사용한다. 원본뿐 아니라 OCR 미리보기·사진·분할 PDF·신청 첨부 저장에도 같은 제한을 적용한다. 자료를 삭제해 여유 공간이 생기면 새 저장이 가능하다.

이 상한은 관리 대상 FILE_ROOT의 파일에 적용한다. DB 파일, 로그, JVM·Python 패키지 및 호스팅 백업까지 512MiB로 제한하는 기능은 아니다. 이 구성은 공유 파일 경로당 Java 앱 프로세스 한 개를 전제로 한다. 여러 앱 인스턴스가 같은 파일 경로를 공유하도록 확장할 때는 프로세스 간 저장·수거 잠금 또는 오브젝트 저장소와 참조 DB를 적용해야 한다.

## 화면과 개인정보 안내

로그인 모달, 마이페이지, 나의 신청, 이용약관, 개인정보 처리방침에 매일 04:00 초기화와 진행 중 작업의 후속 정리를 안내한다. 개인정보 입력 금지·공개 계정 공유 안내는 유지한다. 개인정보 처리방침은 공유 파일의 참조 보존과 미참조 파일의 후속 정리도 구분한다.

## 검증

로컬 실제 MariaDB 테스트에서 동일 내용 파일 공유, 한 신청 삭제 후 다른 참조 보존, 마지막 참조 삭제 후 파일 수거, 반복 초기화, 새 신청·진행 중 작업 보존, 완료 후 정리, 모든 관련 FK의 정상 삭제, 계정·공고 보존, 캐시 소유자/버전 분리와 새 원본 연결, 저장 상한 및 동일 파일 재사용을 검증한다.

실제 공급자 인식과 브라우저 동작 검증은 별도 증거로 기록한다. 테스트용 인식 결과를 실제 공급자 실행으로 표시하지 않는다. 운영 서버 배포나 오전 4시 실제 시각 도달 검증을 완료한 것으로 해석하지 않는다.

실제 로컬 공급자 검증: 이미지 기반 스캔 PDF를 같은 공개 계정으로 두 번 접수하고 매번 명시적으로 검토를 요청했다. 첫 실행은 52.40초, 생성 파일 13개였다. 두 번째는 1.17초에 완료했고, 파일 369개·202,989,248바이트가 그대로 유지되어 추가 파일 0개·추가 용량 0바이트였다. 서버 로그에서 두 번째 작업의 실제 인식 결과 재사용을 확인했다. 출력 증거: output/verification/동일문서-저장재사용.json. 이 값은 검증 당시 로컬 저장량이며 운영 용량 측정이 아니다.

검증 결과: 전체 Java 회귀 59개 통과 후 수거 동시성 테스트와 오류 안내 보완을 추가했고 관련 회귀를 재실행해 누적 60개 모두 실패 0건이다. Python API 경계 테스트 7개도 통과했다. Chrome에서 로그인 모달의 04시 안내와 확인 후 홈 이동, 재사용된 접수의 모든 페이지 미리보기 정상 로드를 확인했다. 오전 04시 실제 시각의 운영 스케줄 실행은 아직 관찰하지 않았으며, 기준 시각과 삭제 대상·진행 작업 보호는 실제 테스트 DB에서 검증했다. 커밋·푸시는 하지 않았다.
