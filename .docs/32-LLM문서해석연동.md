# LLM 문서 해석 연동

## 적용 목적

기존 PaddleOCR·PDF 텍스트 추출과 규칙 기반 항목 추출은 유지한다. LLM은 서식의 라벨과 배치가 달라도 문맥으로 항목을 찾고 문서 종류를 제안하는 역할을 맡는다. 이미지 인식·사진 자르기는 기존 문서 처리기가 맡는다. 텍스트만 받은 LLM이 사진 위치를 찾았다고 표시하지 않는다.

## 처리 흐름

1. 사용자가 원본을 확인하고 문서 검토를 요청한다.
2. PDF 텍스트 또는 PaddleOCR로 페이지별 원문·위치·기본 항목을 추출한다.
3. AI가 활성화된 실제 검토에만 문서 전체의 원문을 한 번 전송한다. 페이지마다 별도로 호출하지 않는다.
4. LLM은 페이지 종류·항목 후보·원문 줄 번호를 JSON으로 반환한다.
5. 서버는 허용된 항목, 페이지·줄 범위, 원문에 값이 실제 존재하는지, 날짜·금액 형식을 검증한다.
6. 누락 항목만 원문 근거와 함께 보완한다. 기존 값과 다른 후보는 덮어쓰지 않고 검토 차이로 남긴다. 문서 종류는 근거와 함께 제안하고 사용자가 경계를 확인한다.
7. 사용자가 원본과 대조하고 수정한 뒤 신청서에 반영한다. 승인·자격 판단은 LLM에 맡기지 않는다.

## 기존 기능과의 차이

| 기존 처리 | LLM 추가 역할 |
| --- | --- |
| 라벨·좌표 규칙으로 필드 추출 | 다른 표현·배치에서도 문맥으로 항목 후보 탐색 |
| 제목 단어로 페이지 종류 추정 | 전체 원문에서 종류와 근거 제안 |
| 여러 문서의 값 차이 확인 | 규칙 추출과 LLM 후보 사이의 차이도 확인 |
| 규칙이 놓친 값은 직접 입력 | 원문에서 검증된 누락값 보완 |

원문에 있다는 사실은 그 값의 업무 의미까지 정확하다는 보장은 아니다. 공급자 상호와 신청자 상호 등을 잘못 연결할 수 있으므로 사용자 확인을 유지한다. 원문에서 찾을 수 없는 생성값은 채택하지 않는다.

## 공급자와 실패 처리

NVIDIA NIM과 OpenRouter는 동일 계약을 사용하는 교체 가능한 공급자다. 키는 서버 환경변수로만 읽으며 브라우저·결과 JSON·로그에는 포함하지 않는다. API 원문 오류도 화면에 노출하지 않는다.

AI 비활성·시간 초과·429·잘못된 JSON·근거 부재 시 기본 OCR 결과는 유지한다. 결과에 공급자·모델·성공 여부·검증 건수·제외 건수·차이를 기록한다. 실패를 성공으로 표시하지 않는다. 공급자 사이 자동 전환은 하지 않아 뜻하지 않은 추가 과금과 중복 전송을 막는다.

## 다른 포트폴리오와의 호출 예산

계정의 40 RPM을 서비스 전용 한도로 사용하지 않는다. 기본 6 RPM, 동시 1건, 호출 간 최소 10초로 제한한다. 문서당 1회만 호출하며 자동 재시도하지 않는다. 429의 Retry-After는 대기 제한으로 저장한다. 제한에 걸리면 대기 스레드를 늘리지 않고 기본 결과와 제한 상태를 반환한다.

SQLite 예약을 BEGIN IMMEDIATE로 처리하여 같은 예산 파일을 사용하는 여러 프로세스가 동시에 통과하지 못하게 한다. 예약·최근 호출·공급자 대기시간은 재시작 후에도 남고, 프로세스가 죽어도 lease 만료 후 복구한다. 예산 파일 오류는 호출을 허용하지 않는 방향으로 처리한다.

`AI_RATE_STATE_PATH`를 지정하지 않으면 사용자 홈의 `.cache/portfolio-ai/provider-budget.sqlite3`를 사용한다. 다른 로컬 포트폴리오도 같은 제한기를 사용해야 합산 제어가 가능하다. 다른 호스트나 제한기를 쓰지 않는 프로젝트의 호출은 이 파일로 집계할 수 없다. 그러므로 이 설정만으로 계정 전체 40 RPM 준수를 보장하지 않는다. 여러 서버에서 합산하려면 공통 게이트웨이 또는 원격 공유 저장소가 필요하다.

## 실행 구분

- 로컬 실제 호출은 가상 신청서만 사용한다.
- OCR 검토 데모는 새 OCR·LLM 호출을 하지 않는다. LLM 결과까지 보여주려면 실제 생성·검증한 결과를 사전 산출물에 포함해야 한다. 기존 OCR 전용 산출물에 AI 성공 표시를 붙이지 않는다.
- 초기 로컬 연동 시 공개 서버의 AI 비활성 설정은 유지했다. 이후 Oracle 새 이미지 검증과 운영 설정 변경은 31·33번 문서의 후속 기록을 따른다.
- 공급자 키·로컬 예산 DB·원시 응답 검증 파일은 Git에 포함하지 않는다.

## 코드 위치

- `ocr/document_ai.py`: 문서 구조화 요청·원문 검증
- `ocr/provider_budget.py`: 프로세스 간 공급자 예산·동시성·429 대기 제한
- `ocr/api.py`: 내부 인증 API와 실제 처리 이벤트
- `IntakeProvider`: Java의 내부 API 호출
- `IntakeAiPolicy`: 기존 값 보존·누락 보완
- `IntakeWorker`: 결과·근거·차이 저장

## 검증 기록

2026-10-26 로컬 검증. 입력은 프로젝트의 가상 문서만 사용했다.

| 검증 | 결과 |
| --- | --- |
| Python 회귀 | 33개 통과: 인증·입력 제한·원문 대조·응답 오류·공유 예약·동시성·6 RPM 창·429 대기 |
| Java 회귀 | AI 정책 2개 + 문서 접수 4개 + 데모/실제 모드 4개, 총 10개 통과 |
| OpenRouter 실제 호출 / 텍스트 PDF | Gemma 4 26B A4B IT, 약 40.65초, 원문 검증 22건·제외 7건 |
| 스캔 PDF 통합 | Java → 실제 PaddleOCR 6쪽 → OpenRouter → 결과 DB 저장, 원문 검증 20건·제외 2건 |
| 규칙과의 비교 | 규칙에 없는 표현 7줄에서 기본 추출 0개, Gemma 4 원문 검증·누락 보완 6개 |
| 후속 업무 | 분할 PDF 쪽수 1·2·1·1·1, 사진 반영, 최종 제출, 담당자 배정 전후 접근 검사 통과 |
| NVIDIA NIM 실제 호출 | Gemma 4 31B IT, 6쪽 및 1쪽 입력에서 시간 초과. 공급자 성공으로 기록하지 않음 |
| 화면 | 저장 결과 재조회, AI 요약·분류 제안·근거·기본 분류와 다른 쪽 표시 확인 |

규칙에 없는 표현 비교는 ‘경영 주체’, ‘운영 책임자’, ‘사업 개시’, ‘연락받을 번호’, ‘요청하는 지원금’, ‘신청인이 부담하는 금액’을 사용했다. 단일 가상 사례로 일반 정확도를 주장하지 않는다.

실제 3쪽은 규칙이 사업계획서로 분류했지만 LLM은 견적서로 제안했다. 자동으로 경계를 바꾸지 않고 ‘확인 필요’로 표시되는 것을 확인했다. 이는 LLM도 틀릴 수 있어 원문과 사용자 확인을 유지해야 하는 실제 사례다.

NIM 호출을 자동 재시도하거나 OpenRouter로 자동 전환하지 않았다. 검증 후 로컬 공급자를 명시적으로 OpenRouter로 선택했다. 키는 기존 `.env.local`, 선택 설정은 무시되는 `.env.ai.local`에서 읽는다. 공개 배포 환경은 이번 로컬 작업에서 변경하지 않았다.

## PDF 처리 후속 변경

PDF 처리 모듈은 Apache PDFBox 3.0.8로 전환했다. 교체 후 실제 스캔 PDF와 OpenRouter를 다시 검증했으며 새 결과는 원문 검증 22건·누락 보완 1건·값 차이 3건이었다. 앞선 20건 측정은 이전 렌더링을 사용한 당시 결과로 보존한다. 상세는 [33번 문서](33-PDFBox전환및회귀검증.md)를 따른다.

7종 제공 문서는 이후 PDFBox와 실제 PaddleOCR·OpenRouter로 다시 준비했다. `scripts/prepare-intake-ai-results.py`는 저장된 실제 인식 원문으로 AI 후보를 생성·검증하며, 제공 문서 코드에서 정답을 읽지 않는다. 데모 요청에서는 이 사전 결과를 불러올 뿐 새 공급자 호출을 하지 않는다. 결과 표는 33번 문서를 참고한다.

## 오라클 PDFBox 이미지 검증 — 2026-10-26

Oracle의 새 OCR 이미지에서 OpenRouter Gemma 4 실제 호출을 추가 검증했다. 텍스트 PDF 6쪽 처리와 AI 합산 48.62초, 원문 검증 23건·제외 1건·누락 보완 0건이었다. 입력이 다른 로컬 측정과 구분한다. NIM 성공으로 표시하지 않으며 자동 공급자 전환도 하지 않았다. 상세는 [33번 문서](33-PDFBox전환및회귀검증.md)를 따른다.

운영 후속 반영에서는 OpenRouter 공급자와 Gemma 4 모델을 활성화했다. 개인정보 처리방침과 실제 검토 확인 문구에 추출 문구의 외부 AI 전송을 표시했다. 데모는 여전히 새 공급자 호출을 하지 않는다. 공급자 응답 성공과 앱의 최종 결과 저장은 구분하며 운영 전체 흐름은 31·33번 기록을 따른다.

최종 공개 앱의 실제 검토에서도 OpenRouter Gemma 4 결과를 DB에 저장했다. 검토 작업 6번은 SUCCEEDED·원문 검증 20건이며, 앱의 PDF 처리·분할·결과 조회까지 합산 103.29초였다. 공급자 단독 응답 시간과 구분한다.
