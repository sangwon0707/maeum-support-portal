# 기획서 — 소상공인 지원사업 신청·서류검토 시스템

> 보존 기록: 본문의 예정·미구현·검토 대기·배포 상태는 작성 당시의 기록이다. 현재 기능과 운영 상태는 원래 번호 문서 및 15·31~33번을 따른다.


> 초기 설계의 범위·수용 기준을 보존한 문서다. 현재 코드와 검증 이력은 [구현 검증 결과](../15-구현검증결과.md), 새 예시 서류와 미연동 범위는 [예시 자료](../17-예시신청서및검증자료.md)를 따른다. 모든 수용 기준이 완료됐다는 뜻은 아니다.

설계 기준 0.1 · 현황 갱신 2026-10-23

## 1. 프로젝트 목적

신청자와 담당자가 신청·서류 제출·보완·검토를 끝까지 처리할 수 있는 Java 기반 웹 시스템을 만든다. JSP·Spring·MyBatis 기반 업무 계층과 명시적인 SQL·트랜잭션·운영 절차를 구성한다. KRDS로 화면의 일관성을 확보하고 OCR은 서류 대조를 돕는 보조 기능으로 설계한다. 실제 정부 서비스가 아닌 가상 지원사업을 대상으로 한다.

## 2. 문제와 사용자

- 신청자: 필수 서류 누락, 입력 내용과 서류 불일치, 보완 사항을 찾기 어려운 문제.
- 담당자: 서류와 신청서를 대조하고 접수·보완 상태를 추적하는 반복 업무.
- 관리자: 공고·접수 기간·필수 서류·업무 배정과 변경 이력을 관리할 필요.

사업 예시: 소상공인 매장 환경개선 지원사업. 간판·시설 개선 계획과 신청금액을 제출한다. 사업 1종·신청서 1종으로 시작하며 자동 자격 판정이나 지원금 지급은 하지 않는다.

## 3. 범위와 우선순위

| 구분 | 포함 내용 | 완료 증거 |
|---|---|---|
| P0 핵심 업무 | 공고, 로그인, 신청 임시저장·제출, 비공개 첨부, 담당자 배정·검토, 보완·재제출, 결과 | 역할별 브라우저 시연·업무 통합 테스트 |
| P0 SQL·운영 | 조건 검색·페이징, 상태/담당자 집계, 기한 초과 목록, 인덱스 검토, Linux/Tomcat 운영 계획 | SQL·실행계획·운영 절차 및 실제 검증 기록 |
| P1 차별화 | 샘플 OCR, 추출값 확인, 5종 예시 체험, KRDS 적용·접근성 | 가상 서류·샘플 표시·체험 격리·브라우저 점검 |
| P2 외부 검증 | 실제 OCR, Oracle 주요 SQL 호환성 | 실제 엔진/DB에서 실행한 별도 결과 |
| 제외 | 지급·결제, 실명인증, 자격 자동 판정, 문자, 복잡한 심사위원 평가 | 후속 변경 요청으로만 추가 |

## 4. 서비스 정책

- 신청자는 사업당 한 건의 신청서를 가진다. 임시저장은 수정 가능하며 제출 후에는 수정할 수 없다.
- 보완 요청 시 지정된 항목만 수정하며 보완 기한을 별도로 적용한다.
- 담당자는 배정된 신청만 검토한다. 관리자는 공고·배정을 관리하며 선정 결과는 담당자가 확정한다.
- OCR 실패는 신청을 차단하지 않는다. 직접 확인한 값을 입력하고 제출할 수 있다.
- 데모는 가상 정보만 사용하며 개인별 공간에서 역할을 전환한다. 실제 권한을 승격하지 않는다.
- 화면 날짜는 한국 시간, 저장 시각은 UTC다. 기한 경계는 종료 시각 미만까지 허용한다.

## 5. 구성과 기술 결정

Java 21 / eGovFrame 5.0 / Spring MVC / JSP·JSTL / KRDS / MyBatis / MariaDB / Maven WAR / Tomcat. 서버 세션과 CSRF 검증을 사용한다. 하나의 배포 단위 안에서 업무 모듈을 나눈다. 정확한 패치 버전은 공식 배포 POM과 실행 검증을 거쳐 고정한다.

MariaDB를 기본 DB로 조정한다. PostgreSQL은 초기안에서 대체하며 DB 두 종류의 동시 지원은 1차 범위가 아니다. Oracle은 후속 검증 대상으로만 명시한다. Spring Boot·jQuery는 공고에 등장하지만 기술 개수를 늘리기 위해 추가하지 않는다. JSP/JSTL·JavaScript·Fetch로 현재 범위를 구현한다. 기존 Java EE/javax 기반 코드와 Jakarta 기반 구성의 차이를 설명하는 문서를 후속 작성한다.

## 6. 시연과 수용 기준

가상 예시 선택 → 신청서 확인 → 상호 불일치 확인·수정 → 제출 → 담당자 보완 요청 → 신청자 재제출 → 결과 확정. 오류·누락·기한 초과·중복 처리를 별도 시나리오로 보여준다.

성공 기준: 핵심 상태 전이·권한 테스트 통과, 5종 데모 예상 결과 일치, 역할 간 데이터 격리, 모바일/키보드 신청 완료, MariaDB SQL 근거, Linux/Tomcat 실행·재시작 증거. 페이지 수나 기술 개수를 성과 지표로 삼지 않는다.

## 7. 진행 단계

설계 초안 → 문서·와이어프레임 검토 → 기술 호환성 확인 → 핵심 업무 구현 → SQL·운영 검증 → 데모·OCR → 접근성·최종 시연. 일정은 작업량 확인 후 산정한다. 외부 OCR 공급자·배포 공급자·보관 기간은 미확정 결정 목록으로 관리한다.

현재 구현·검증 범위는 [구현 검증 결과](../15-구현검증결과.md)를 참고한다. 본문은 구현 전 설계 기준을 보존한다.
