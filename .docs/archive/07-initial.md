# SQL·배포·유지보수 계획

> 보존 기록: 본문의 예정·미구현·검토 대기·배포 상태는 작성 당시의 기록이다. 현재 기능과 운영 상태는 원래 번호 문서 및 15·31~33번을 따른다.


> 초기 설계의 범위·수용 기준을 보존한 문서다. 현재 코드와 검증 이력은 [구현 검증 결과](../15-구현검증결과.md), 새 예시 서류와 미연동 범위는 [예시 자료](../17-예시신청서및검증자료.md)를 따른다. 모든 수용 기준이 완료됐다는 뜻은 아니다.

## 2. SQL 작업 목록

SQL-01 조건 검색·페이지: 상태/기간/상호/접수번호, 담당 배정 조건, 정렬 동률 처리, count 일치.
SQL-02 현재 상태별 건수: 같은 모집 사업·공간·담당 범위를 적용하며 합계가 신청 수와 일치.
SQL-03 담당자별 건수: 미배정 별도 표시, JOIN에 의한 중복 집계 방지.
SQL-04 보완 기한 초과: NEEDS_SUPPLEMENT + OPEN + due_at ≤ 기준 시각. 데모 제외.

실측 전에 성능 개선 수치를 만들지 않는다. 가상 데이터를 사용하고 EXPLAIN 결과·인덱스 전후·쓰기 비용·기능 정합성을 함께 기록한다. Oracle 프로필과 Mapper 분기는 실제 이식 요구가 확정될 때 추가한다.

## 3. 운영 절차 수립 순서

1. Java·Tomcat·MariaDB 버전과 공식 호환성 확인, 의존성 트리 저장.
2. Linux 전용 서비스 계정, 웹루트 외 파일 경로·최소 권한, 시크릿 외부 주입.
3. DB 백업 → migration → WAR 배포 → health/로그/로그인/신청 smoke test.
4. 이전 WAR 보관. DB 변경은 역호환 우선이며 실패 시 복원 절차를 따름. Flyway migrate가 자동 롤백을 보장한다고 가정하지 않음.
5. HTTPS·세션 쿠키·CSRF·프록시 설정 확인. 부하·실패·로그 로테이션·디스크 용량 확인.
6. DB·비공개 파일의 일관된 백업: 쓰기·OCR 정지 구간에서 함께 백업, 별도 환경에 복원 후 첨부 접근 확인.
7. 재시작 후 lease 만료 작업 회수, 개인정보 없는 오류 로그와 요청 ID 추적 확인.

health endpoint는 상태만 공개하고 계정·연결 정보·환경변수는 노출하지 않는다. 관리자·감사 조회는 외부 공개하지 않는다. 실제 배포 대상·명령은 공급자 확정 후 runbook으로 작성한다.

## 4. 유지보수 사례 템플릿
