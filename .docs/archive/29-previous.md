# 이전 작성 기록

> 보존 기록: 본문의 예정·미구현·검토 대기·배포 상태는 작성 당시의 기록이다. 현재 기능과 운영 상태는 원래 번호 문서 및 15·31~33번을 따른다.


이 문서는 작성 당시 상태를 보존한 기록이다. 현재 설명은 원래 번호의 문서를 따른다.

# 문서 기반 신청 구현 계획

> 후속 변경: PDF 처리 부분은 Apache PDFBox Java 모듈로 전환했다. 현재 구조와 검증은 [33번 문서](../33-PDFBox전환및회귀검증.md)를 따른다. 아래는 초기 설계와 변경 과정의 기록이다.


## 목표

지원사업 신청은 직접 입력과 작성 문서 업로드를 함께 제공한다. 처리 대상은 사업자등록증 네 항목에 한정하지 않고 신청서·계획서·동의서·견적서·사진을 포함한다. 시나리오를 선택해 정답을 주입하는 공개 체험 경로는 제공하지 않는다.

## 입력과 처리 계약

- 직접 입력: 기존 신청서 작성 후 증빙을 개별 첨부하거나 문서 분석을 추가한다.
- 통합 파일: 여러 서류를 포함한 PDF 1개를 제출한다.
- 개별 파일: 최대 5개 PDF·PNG·JPEG를 제출하고 파일마다 종류 또는 자동 분류를 선택한다.
- 파일당 10MiB, 요청 전체 51MiB, 작업 전체 최대 12쪽. 암호 PDF·위장 이미지·과도한 페이지 크기는 거절한다.
- 원본을 보존하고 페이지를 읽은 뒤 문서 경계를 제안한다. 같은 서류의 연속 페이지는 하나의 문서로 묶는다. 사용자가 종류·경계를 수정할 수 있어야 한다.
- 분할 결과는 실제 PDF로 내려받을 수 있어야 한다. 모든 페이지·문서·사진·추출 항목은 원본 파일·페이지와 연결한다.
- 텍스트 PDF는 원문 좌표를 읽고 이미지 페이지는 PaddleOCR로 처리한다. 사진은 포함 이미지 영역 또는 OpenCV 후보 영역에서 추출하고 사용자가 포함 여부를 확인한다.
- 정답 JSON·파일명·예시 코드에서 추출값을 읽지 않는다. 외부 AI는 기본 경로에서 호출하지 않는다.

## 화면과 진행률

공고에서 입력 방식을 선택한다. 문서 업로드 후 파일·처리 단계·완료 페이지 수를 표시하고 실제 완료 페이지 비율로 진행률을 갱신한다. 추출이 끝나면 분할 문서, 원본 페이지, 신청 내용, 견적 원문, 추출 사진을 하나의 검토 화면에 구성한다. 값이 없거나 충돌하면 직접 확인하게 한다. 가짜 퍼센트·시간 기반 완료·자동 선정은 사용하지 않는다.

## 반영·제출·권한

분석만으로 기존 신청값을 덮어쓰거나 제출하지 않는다. 사용자가 추출값과 분류를 검토한 뒤 반영하면 같은 신청 Service를 거쳐 저장한다. 사업자등록증·견적서 페이지는 기존 첨부로 연결하고 사용자 확인값도 저장한다. 전체 원본·분할 PDF·사진은 분석 건과 제출본 식별자로 보존한다. 제출 이후 분석·반영은 금지하고 타인의 원본·상태·산출물은 조회할 수 없다.

## 완료 기준

1. 실제 통합 신청서의 모든 페이지가 처리되고 서류 단위 PDF가 생성된다.
2. 같은 종류의 연속 페이지는 한 문서이며 사용자가 경계를 수정할 수 있다.
3. 신청 정보·사업비·계획·사진이 원본에서 추출되고 검토 화면에서 수정 가능하다.
4. 검토 결과를 반영하고 기존 제출·담당자 검토 흐름으로 이어진다.
5. 개별 업로드와 직접 입력도 같은 신청·첨부·검토 체계를 사용한다.
6. 손상 파일·미지원 파일·페이지 초과·분류 불명·누락·타인 접근·중복 반영·버전 충돌·처리 실패를 검사한다.
7. 실제 DB·실제 OCR·브라우저 검증 결과를 구분해 기록한다. 미완료를 완료로 표현하지 않는다.

## 구현 및 검증 기록 — 2026-10-26

### 구현한 처리 경로

공고의 ‘작성 문서 업로드’는 파일 선택 모달을 먼저 연다. 모달을 열거나 닫는 동작만으로 기존 분석 결과로 이동하거나 신청·분석 작업을 생성하지 않는다. 예시 파일 선택 또는 직접 선택한 파일의 분석 요청 후에만 `POST /programs/{programId}/intake`로 실제 파일을 제출한다. 예시는 이미지 기반 스캔 PDF가 기본이다. 비정형 스캔 5종은 기존 기울어짐·여백을 보존한 용량 최적화 사본이며 원본을 변경하지 않는다. 환경개선 기본·비교 예시는 이미지형 PDF다.

- `document_intake`와 `intake_source`에 처리 상태·원본·작업 식별자를 저장한다. 작업 claim과 만료 상태를 검사하고 처리 진행률은 페이지 이벤트로 갱신한다.
- 내부 Python API의 PyMuPDF가 PDF 원문·렌더링·실제 페이지 분할을 담당한다. 텍스트 없는 페이지는 PaddleOCR를 실행한다. 사진은 PDF 이미지 영역 또는 OpenCV 후보 영역에서 분리한다.
- 연속된 계획서 페이지는 한 PDF로 유지한다. 사용자가 문서 종류·시작 경계를 바꿀 수 있고 변경 경계로 PDF를 다시 생성한다.
- 검토 화면은 왼쪽 원본 뷰어·세로 페이지 목록, 오른쪽 신청 내용·서류 분할·사진/표 탭으로 구성한다. 좁은 화면의 페이지 목록은 원본 위쪽에 배치한다. 신청 항목은 작은 출처 버튼을 둔 인라인 입력으로 정리한다.
- 반영은 소유자의 DRAFT에서만 가능하다. 반영 후에도 최종 제출 전에는 ‘신청 내용 수정 → 저장’과 수정 취소를 제공한다. 사용자 수정값과 추출 원문을 구분해 보존한다.
- 최종 확인에서 원본 검토 화면으로 돌아갈 수 있다. 제출본에는 `sourceIntakeId`를 저장한다. 원본·파생 파일은 신청 조회 권한을 매번 검사한다.
- 공개 시나리오 `/demo` 경로는 제공하지 않는다. 내부 기존 테스트 픽스처는 실제 OCR 결과로 취급하지 않는다.

### 확인한 증거

- 실제 MariaDB를 사용하는 Java 테스트 51개 통과. 문서 권한·등록되지 않은 파일 키·버전 충돌 롤백·중복 반영·반영 후 수정 소유권을 포함한다.
- Python 테스트 26개 통과. 네이티브 PDF의 텍스트·사진·표 행 추출, 7종 예시, 암호·손상·페이지 초과 거부, 실제 2쪽 PDF 분할 및 내부 API 인증을 포함한다. 테스트 엔진 사용과 실제 PaddleOCR 실행은 별도다.
- 텍스트 PDF 실제 업로드: 6쪽 → 5개 문서. 내려받은 파일을 다시 열어 원본 6쪽과 분할 1·2·1·1·1쪽을 확인했다.
- 서로 분리된 PDF 5개 실제 업로드: 총 6쪽 → 문서 5개. 브라우저에서 계획서 중간에 새 문서 경계를 추가해 반영한 뒤 6개 문서로 바뀌는 것을 확인했다.
- 실제 업로드 → 검토값 반영 → 필수 첨부 연결·선택 사진 표시 → 최종 제출 → 관리자 배정 → 담당자 원본 조회를 로컬 HTTP로 확인했다. 배정 전 담당자 원본·분석 조회는 403이었다.
- 이미지 기반 비정형 스캔 6쪽을 내부 API로 처리해 모든 페이지가 `PADDLE_OCR`였고 사진 1개가 분리됐다. 당시 약 56초로, 장비·모델 준비 상태에 따라 달라진다.
- 브라우저에서 수정 시작 → 연락처 변경 → 취소 복원, 다시 변경 → 저장 → 제출 전 확인의 값 유지, 이전 단계 링크를 확인했다.

### 현재 처리 범위

파일당 10MiB·최대 12쪽이며, 스캔 압축 사본은 대략 1MiB다. 손상 파일과 일부 페이지의 인식 오류는 자동으로 정답으로 대체하지 않는다. 레이아웃 기반 분류·사진 후보·금액 추출은 원본 대조와 사용자 수정을 거치는 방식이다. 견적 표는 좌표를 기준으로 묶은 원문 행을 제공하며 완전한 품목·수량·단가 업무 데이터 모델로 확정하는 기능은 포함하지 않는다. 외부 AI 호출·원격 DB·배포 검증과 커밋·푸시는 이번 로컬 검증에 포함하지 않는다.

추가 브라우저 검증: `/programs/6`에서 업로드 버튼을 누르면 주소를 유지한 채 모달이 열렸다. 예시 신청서·내 파일 선택 전환 및 닫기를 확인했다. 예시의 비정형 스캔본을 선택해 생성된 새 분석 건은 6쪽 모두 실제 OCR로 처리됐고, 원본 사진 1개와 1·2·1·1·1쪽 분할 PDF가 생성됐다. 다운로드한 원본의 각 페이지 렌더링이 선택한 스캔 예시와 일치하는 것도 확인했다. 결과 화면에는 띄어쓰기 등 OCR 차이가 그대로 남을 수 있어 원본 대조와 수정 단계를 유지한다.

## 최종 시작 동선

파일 탐색기 모달의 업로드는 원본 저장만 수행한다. 다음 화면은 UPLOADED 상태의 PDF 원본을 페이지 맞춤으로 보여준다. 사용자가 이 화면의 ‘분석 시작’을 눌러야 QUEUED가 되고 OCR 진행률이 표시된다. 업로드 모달에 분석 시작 버튼을 두지 않는다. 시작 전에는 진행률·로딩 서클을 표시하지 않으며 새로고침·뒤로가기·서버 재시작으로도 OCR이 자동 실행되지 않는다. 테스트 스크립트도 업로드 직후 UPLOADED와 진행률 없음부터 확인하고 별도의 시작 요청을 보낸다.
